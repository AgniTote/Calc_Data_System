# Технические протоколы Excel–Access

Этот документ определяет обязательное поведение VBA, DAO, Power Query и служебных таблиц. Предметная модель описана в [01_Действующая_архитектура.md](architecture.md).

## 1. Служебные таблицы

Все служебные таблицы этого раздела находятся в основном файле «Учет.accdb». Файл «ИсторияИсправлений.accdb» содержит технические архивы.

### 1.1. Журнал операций

Одна строка соответствует одной логической попытке записи: нажатию «Отправить» или сохранению через контролируемую форму Access.

| Поле | Тип | Назначение |
|---|---|---|
| ID операции | `AutoNumber`, PK | Идентификатор попытки |
| Код файла | Short Text, допускает `Null` для Access | Источник операции |
| Версия файла | Short Text, допускает `Null` для Access | Версия Excel-сборки |
| Автор | Short Text | Имя пользователя Windows |
| Тип операции | Short Text | Вид логической операции |
| Начато | Date/Time | Время начала попытки |
| Применено | Date/Time, `Null` | Заполняется только внутри успешной транзакции |
| Количество строк | Long Integer | Плановое или обработанное количество |
| Описание ошибки | Long Text, `Null` | Причина контролируемого сбоя |

Пустое `Применено` означает, что бизнес-изменения не были подтверждены. Журнал не фиксирует чтение, открытие файла, построение и печать отчёта.

### 1.2. Состояние базы

Таблица содержит ровно одну строку с ID `1`.

| Поле | Тип | Назначение |
|---|---|---|
| ID | Long Integer, PK | Всегда `1` |
| Версия данных | Long Integer | Счётчик успешных логических записей, начальное значение `1` |
| Последняя операция | Long Integer, `Null`, FK | Последняя применённая операция |
| Дата изменения | Date/Time | Время последнего подтверждённого изменения |

### 1.3. Верифицированные файлы Excel

| Поле | Тип | Назначение |
|---|---|---|
| ID | `AutoNumber`, PK | Внутренний ID |
| Код файла | Short Text, unique, required | Постоянный машинный код, например `PAYROLL_CALC` |
| Название файла | Short Text, required | Понятное название |
| Актуальная версия | Short Text, required | Единственная разрешённая версия; сравнение как текста |
| Разрешён | Yes/No, required | Возможность полностью отключить файл |
| Дата изменения | Date/Time | Время изменения допуска |

Версия хранится текстом, чтобы `1.1` и `1.10` не смешивались. Имя файла на диске не используется как идентификатор.

## 2. Парольное подключение к Access

Основной файл «Учет.accdb» и отдельный файл «ИсторияИсправлений.accdb» создаются с паролем базы. Пути и параметры подключения к обоим файлам задаются централизованно. Текущий пароль является общим секретом всех разрешённых Excel-файлов и контролируемого интерфейса Access.

Общий VBA-модуль подключения обязан:

1. Получать пароль только из закрытого технического модуля проекта VBA.
2. Формировать строку подключения в памяти и передавать пароль провайдеру Access при открытии DAO-соединения или источника Power Query.
3. Не записывать пароль на листы, в именованные диапазоны, пользовательские настройки, журнал операций или текст ошибки.
4. При неверном или отсутствующем пароле прекращать чтение и запись без попытки открыть базу в незащищённом режиме.
5. Сразу после подключения выполнять обычную проверку кода и версии Excel-файла. Знание пароля само по себе не разрешает работу с бизнес-данными.

Проект VBA распространяемой книги защищается паролем от обычного просмотра и изменения. Это затрудняет случайное извлечение секрета, но не считается криптографической защитой: пользователь с достаточными техническими знаниями может получить пароль из файла или памяти процесса.

При смене пароля выполняется единая процедура ротации:

1. Остановить работу системы, закрыть все соединения к обоим файлам и убедиться в отсутствии их `.laccdb`.
2. Открыть затрагиваемые файлы монопольно и установить новые пароли; работу возобновлять только после согласованного обновления параметров подключения.
3. Обновить пароль во всех актуальных Excel-файлах и контролируемом интерфейсе Access.
4. Повысить версии изменённых файлов и зарегистрировать их как актуальные.
5. Отключить прежние версии в реестре и только после этого возобновить работу пользователей.

Пароль базы не различает пользователей и не подтверждает личность конкретного Excel-файла. Автор операции по-прежнему определяется именем пользователя Windows, а идентичность и совместимость книги — её кодом и версией.

## 3. Проверка версии Excel-файла

Каждый файл ввода, расчёта и отчёта содержит лист `VeryHidden` с полями:

- `Код файла`;
- `Название файла`;
- `Версия файла`.

Перед каждой операцией с бизнес-данными общий VBA-модуль:

1. Считывает технические реквизиты книги.
2. Обращается только к таблице «Верифицированные файлы Excel».
3. Требует ровно одну строку с совпадающим кодом.
4. Проверяет `Разрешён = Да`.
5. Сравнивает версии точным текстовым равенством.

Проверка выполняется перед каждой загрузкой справочников, выгрузкой строк для правки, управляемым обновлением Power Query и транзакцией записи. Одной проверки при открытии книги недостаточно.

Неизвестный код, отключённый файл, несовпадающая версия, неоднозначный результат или недоступность реестра блокируют обмен. Пользователь получает локальную и актуальную версии, если последнюю удалось определить. Уже загруженные в книгу данные помечаются устаревшими и не используются для расчёта, отправки или актуальной печати.

Это защита от случайного использования старых сборок, а не криптографическая защита от намеренного изменения VBA или технического листа.

## 4. Транзакционная запись

Единица транзакции — одна логическая отправка целиком, включая рабочие изменения в «Учет.accdb» и архивные снимки в «ИсторияИсправлений.accdb».

Оба объекта DAO `Database` открываются через один явно используемый `Workspace`. `BeginTrans`, `CommitTrans` и `Rollback` вызываются для этого `Workspace`; отдельные независимые транзакции для файлов запрещены. До изменения архивируемой строки проверяется доступность файла истории для записи. Ошибка подключения, отсутствие необходимой архивной таблицы или ошибка записи снимка блокирует весь пакет. Служебные таблицы, журнал операций и общая версия данных остаются в основном файле.

Алгоритм:

1. Проверить версию Excel-файла.
2. Создать строку журнала с `Начато` и пустым `Применено` до транзакции.
3. Выполнить `BeginTrans`.
4. Проверить строки пакета, определить фактические изменения и их прямые и последующие зависимости.
5. Проверить разрешение изменять исходные и затрагиваемые зависимые периоды по общим правилам. При запрете откатить весь пакет до применения бизнес-изменений.
6. Перед каждым `UPDATE` или `DELETE` технически архивируемой сущности создать архивный снимок.
7. Выполнить все `INSERT`/`UPDATE`/`DELETE`.
8. Сохранить найденные последствия изменения со ссылкой на текущую операцию.
9. Атомарно увеличить `Версия данных`, записать последнюю операцию и дату.
10. Заполнить `Применено` в журнале.
11. Выполнить `CommitTrans dbForceOSFlush`.
12. Показать уведомление о применённом изменении и его последствиях.

При любой ошибке выполняется `Rollback` всего пакета. После контролируемого отката описание ошибки по возможности записывается в уже существующую строку журнала вне отменённой транзакции. Частичная отправка запрещена.

## 5. Защита от потерянного обновления

Каждая изменяемая рабочая таблица получает поле `Версия` типа Long Integer, начальное значение `1`.

Excel или форма читает `ID + Версия`. Изменение выполняется условно:

```sql
UPDATE Рейсы
SET ..., Версия = Версия + 1
WHERE ID = [ожидаемый ID]
  AND Версия = [ожидаемая версия];
```

VBA проверяет `RecordsAffected`:

- `1` — изменение успешно;
- `0` — строка изменена или удалена после чтения;
- больше `1` — ошибка структуры.

Конфликт версии откатывает весь пакет и не повторяется автоматически. Пользователь обновляет данные и повторяет осознанную правку.

## 6. Физические блокировки Access

В базе включается блокировка на уровне записей. VBA перехватывает ошибки DAO 3188, 3260 и 3008.

При физической блокировке повторяется вся транзакция с начала в рамках той же строки журнала. Используется экспоненциальная задержка со случайным разбросом, максимум пять попыток. После исчерпания попыток транзакция откатывается, журнал получает ошибку, пользователь видит предложение повторить позднее.

Физическая блокировка и конфликт `Версии` — разные случаи: блокировку можно повторять автоматически, устаревшую бизнес-строку — нельзя.

## 7. Согласованное чтение Power Query

Несколько запросов Power Query могут прочитать разные состояния базы, если между ними подтвердится чужая транзакция. Поэтому файлы расчёта и отчёта обновляются только общей кнопкой.

Алгоритм:

1. Проверить версию Excel-файла.
2. Установить статус «Срез не проверен».
3. Синхронно прочитать начальную `Версию данных`.
4. Отключить фоновые обновления.
5. Последовательно обновить необходимые запросы, ожидая завершения каждого.
6. Синхронно прочитать конечную `Версию данных`.
7. При равенстве версий установить «Срез проверен», сохранить номер и время проверки.
8. При различии один раз повторить весь цикл.
9. При втором конфликте оставить «Срез не проверен» и заблокировать расчёт, отправку, печать и выгрузку.

Ручное обновление отдельного запроса или стандартное `Обновить всё` сбрасывает подтверждённый статус. Управляющие действия обязаны проверять статус перед использованием данных.

## 8. Архивирование изменений

Для `UPDATE` или `DELETE` сущности с техническим архивом действуют шаги:

1. Прочитать рабочую строку по `ID + Версия`.
2. Проверить наличие операции в журнале основного файла и вставить бизнес-поля строки в соответствующую архивную таблицу файла «ИсторияИсправлений.accdb» вместе с типом операции, автором, временем и ID журнала. Межфайловой внешний ключ не создаётся.
3. Условно изменить или удалить рабочую строку.
4. Проверить `RecordsAffected = 1`.

Все шаги входят в одну транзакцию общего DAO `Workspace` для обоих файлов. При конфликте созданный внутри транзакции архивный снимок также откатывается. Архивный ID исходной строки является историческим значением и не требует существования строки после удаления; ID операции проверяется программно.

Для регистра истории применяется другой алгоритм: текущий период закрывается датой окончания, после чего добавляется новая строка. Эти действия также атомарны.

## 9. Подключение DAO и разрядность

- Используется Late Binding; жёсткие ссылки в `Tools → References` запрещены.
- Функция подключения последовательно пробует доступные версии `DAO.DBEngine`, включая 120 и 160.
- При отсутствии драйвера определяется разрядность процесса Excel и показывается инструкция по установке соответствующего Microsoft Access Database Engine.
- Все WinAPI-вызовы используют `#If VBA7` и `LongPtr` там, где это требуется.
- Сторонние 32-битные ActiveX `.ocx` не используются.

Самодиагностика DAO не перехватывает стандартную ошибку коннектора Power Query. Управляющий VBA-код должен прекращать дальнейшие действия, если обновление Power Query завершилось ошибкой.

## 10. Резервное копирование

В конце недели ответственный пользователь останавливает работу системы и закрывает все соединения к «Учет.accdb» и «ИсторияИсправлений.accdb». Отсутствие `.laccdb` проверяется рядом с каждым файлом. Оба `.accdb` копируются целиком в один комплект с общей датой и идентификатором; между копированием файлов работа не возобновляется. Комплект считается готовым только после успешного копирования обоих файлов. Восстанавливать файлы из разных комплектов запрещено.

Принятый интервал допускает потерю изменений до одной недели при физической утрате базы. Пока не определены резервный исполнитель и действие, если база занята в момент планового копирования.

## 11. Ограничения механизма допуска файлов

Access является файловой базой и не выполняет серверный код при каждом обращении. Поэтому реестр версий обязателен для штатных макросов, но не способен сам по себе запретить технически подготовленному пользователю открыть `.accdb` напрямую или изменить VBA. Организационные права сетевой папки и защита VBA рассматриваются отдельно от проверки совместимости версий.

Пароль базы уменьшает риск случайного прямого доступа, но не устраняет это ограничение: один и тот же секрет должен быть доступен всем штатным Excel-файлам, поэтому он может быть извлечён и использован вне них. Если потребуется защита от намеренного обхода штатных файлов, файловая `.accdb` должна быть заменена серверной СУБД с индивидуальными правами пользователей.

## 12. Обработка исходной вставки из 1С

Исходный диапазон существует только во временной рабочей области файла ввода. Отдельная таблица сырых загрузок, копия исходного диапазона и файловый архив таких вставок не создаются.

При отправке VBA записывает непосредственно нормализованные строки. Их экономическое содержание и состав практически соответствуют исходной форме 1С; счета и субконто выделяются в отдельные свойства и заменяются ссылками на соответствующие справочники там, где это предусмотрено моделью.

Журнал операций хранит сведения о попытке и количество строк, но не исходное содержимое вставки. Технические архивы содержат прежние состояния нормализованных записей Access и также не используются для хранения сырого блока из 1С. При ошибке до успешной отправки исходный диапазон остаётся только в открытом Excel-файле и после его очистки или закрытия системой не восстанавливается.

## 13. Формульная сверка перед отправкой

Каждый файл ввода данных из 1С содержит два независимых набора формул:

1. Формулы контрольных итогов исходного вставленного блока.
2. Формулы тех же итогов по нормализованной таблице, подготовленной к отправке.

Для каждого обязательного показателя отдельная контрольная формула возвращает однозначный результат совпадения. Совпадение определяется после округления обеих сторон до точности исходного отчёта. Пустое значение, текст вместо ожидаемого числа, ошибка Excel или расхождение считаются неуспешной проверкой.

При нажатии «Отправить» VBA принудительно выполняет полный пересчёт книги и читает итоговые контрольные ячейки. VBA не пересчитывает бухгалтерские итоги собственным алгоритмом и не дублирует формулы. Если хотя бы одна проверка не вернула `ИСТИНА`, `BeginTrans` и запись бизнес-данных не выполняются; пользователь получает название показателя, исходный итог, нормализованный итог и разницу.

При успешной проверке применяется обычный транзакционный протокол. Контроль подтверждает только соответствие подготовленного пакета текущей вставке в Excel. Отдельная таблица сверок в Access не создаётся, а контрольные суммы не используются как постоянные бизнес-данные.

## 14. Полная синхронизация ОСВ

Единица загрузки ОСВ — полный снимок выбранной области отчёта. Область однозначно задаётся как минимум периодом, видом формы и организацией, а для ОСВ по отдельному счёту также соответствующим счётом. Состав ключа области уточняется вместе с окончательной структурой Регистра бухгалтерии.

После успешной формульной сверки VBA в одной транзакции сопоставляет входной набор с рабочими строками той же области:

1. Добавляет строки с новыми бизнес-ключами.
2. Для изменённых строк создаёт технический архив и обновляет рабочее состояние.
3. Не переписывает строки, бизнес-поля которых не изменились.
4. Для прежних рабочих строк, отсутствующих в новом полном наборе, создаёт технический архив и удаляет их из рабочей таблицы.
5. Проверяет количество затронутых строк и завершает общий протокол журнала и `Версии данных`.

Сравнение и изменения ограничиваются только загружаемой областью; строки другого периода, организации, вида формы или счёта не затрагиваются. Ошибка на любом шаге откатывает всю синхронизацию.

Система не принимает отдельный признак полноты от пользователя и не ведёт таблицу состояний полноты ОСВ. Возможность изменять период проверяется отдельно по общему протоколу раздела 16. Штатный процесс разрешает отправлять только заранее сформированную полную ОСВ. Повторная отправка означает новую полную редакцию той же области, а не добавление промежуточной части.



## 15. Определение зависимостей и уведомление

Для каждого расчёта и отчёта при проектировании фиксируются источник, влияющие поля, правило определения затронутых объектов и периодов и дальнейшие зависимые результаты. Реестр связей хранится в Access; правила отбора конкретных результатов реализуются в общем VBA-модуле. Точная структура реестра и записи последствий определяется отдельно.

При обработке пакета общий модуль:

1. Сравнивает прежнее и новое состояние и выделяет фактические изменения бизнес-полей, добавления и удаления.
2. Для каждой зависимости определяет затронутые объекты, организации и периоды. При изменении даты, работника или иной принадлежности использует и старые, и новые значения.
3. Учитывает наборы строк: новая строка также может затронуть ранее выполненный расчёт. Для исторических значений проверяет весь изменённый интервал действия.
4. Проходит прямые и последующие зависимости, объединяет повторные находки и исключает бесконечный обход. Циклы в схеме расчётов требуют отдельного решения при проектировании и не допускают молчаливого пропуска уведомления.
5. Проверяет допустимость изменения всех затрагиваемых периодов согласно разделу 16.
6. В одной транзакции с бизнес-изменениями сохраняет последствия и ссылку на журнал операций. При откате запись последствий также откатывается.
7. После успешного подтверждения выдаёт уведомление с перечнем затронутых результатов и требуемых действий. Если последствия не найдены, сообщает об этом явно.

Уведомление описывает возможное влияние, а не заранее известную разницу сумм. Автоматический каскадный пересчёт не является требованием. Подтверждение прочтения сообщения не заменяет проверку или пересчёт результата. Неизменившийся набор бизнес-данных не создаёт уведомления о бизнес-изменении.

Непрочитанные и необработанные последствия доступны из штатных файлов при последующей работе. Если для изменяемого контура ещё не описаны зависимости, система не должна представлять отсутствие правил как подтверждённое отсутствие последствий: такое правило требуется до ввода контура в эксплуатацию.

## 16. Проверка допустимых периодов изменения

Все штатные пути записи используют общие правила допустимых периодов, хранящиеся в Access. Проверка охватывает добавление, изменение, удаление, полную синхронизацию области и запись результатов расчёта.

Перед отправкой Excel может предварительно показать запрет и его причину. Окончательная проверка выполняется внутри транзакции до применения бизнес-изменений и должна учитывать конкурентное изменение правил допуска. Конкретный механизм согласования проверки с изменением правил определяется при реализации общего модуля.

Для операции определяются:

- экономические даты или периоды исходных строк, включая прежний и новый период при переносе;
- периоды действия изменяемых нормативов и исторических атрибутов;
- периоды зависимых данных, на которые изменение может повлиять по описанным правилам.

Если исходный или затрагиваемый зависимый период запрещён для изменения, весь пакет откатывается. Пользователь получает исходный объект, запрещённый период и, при наличии, цепочку зависимости, вызвавшую запрет. Обход через другой Excel-файл, форму Access или повторную загрузку ОСВ не предусмотрен.

При отсутствии необходимого правила допуска отправка соответствующих данных блокируется с сообщением о необходимости настроить периоды. Наличие полной ОСВ или согласованного среза Power Query не заменяет разрешение изменять период.

Область правил, конкретные границы разрешённых периодов, права ответственного и порядок исключительного исправления определяются отдельно. Обычная кнопка «Отправить» не открывает запрещённый период и не изменяет его границы автоматически.
