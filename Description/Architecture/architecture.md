# Действующая архитектура учётной системы

Этот документ содержит только актуальные правила. История выбора решений вынесена в [04_Журнал_архитектурных_решений.md](decisions.md), незакрытые вопросы — в [03_Открытые_вопросы_и_план.md](../Development/open-questions.md), а развиваемый перечень входных данных — в [05_Матрица_источников_данных.md](../Data/sources.md).

## 1. Контекст и границы

Учёт ведётся в 1С на сервере. Конфигурацию 1С менять нельзя. Доступны стандартные формы выгрузки: ОСВ, ОСВ по счёту, Анализ счёта и Карточка счёта.

Первичные бухгалтерские документы вводятся в 1С вручную. Excel-система не дублирует этот ввод. Она:

1. Принимает данные из стандартных форм 1С через ручное копирование.
2. Нормализует их и сохраняет в Access.
3. Собирает дополнительную детализацию, которой в 1С нет.
4. Выполняет управленческие расчёты.
5. Формирует аналитику и отчёты, недоступные непосредственно в 1С.

Из Excel обратно в 1С вручную переносятся только рассчитанные суммы зарплаты, налогов, амортизации и списания материалов. Контроль переноса выполняется сверкой итогов за период.

## 2. Роли компонентов

### 2.1. Файлы ввода

Каждый вид исходных данных получает отдельный переиспользуемый Excel-файл либо объединяется с близкими видами данных, если это удобнее пользователям.

Файл ввода:

- принимает ручной ввод или вставку из 1С;
- читает справочники и существующие строки, необходимые для проверки или правки;
- нормализует данные;
- по кнопке «Отправить» записывает пакет в Access через VBA/DAO;
- по кнопке «Очистить» удаляет пользовательский ввод из шаблона;
- не является постоянным хранилищем.

Перечень известных контуров, их источники, форма и периодичность ведутся в [05_Матрица_источников_данных.md](../Data/sources.md). Список может расширяться по критерию: если необходимой детализации нет в 1С, создаётся соответствующий контур ввода.

### 2.2. Файлы расчёта

Файл расчёта:

1. Читает из Access необходимые факты и справочники через Power Query.
2. При необходимости принимает дополнительные корректировки пользователя.
3. Рассчитывает производный показатель формулами или VBA.
4. Записывает результат обратно в Access через общий транзакционный механизм.
5. Для установленных видов расчёта предоставляет бухгалтеру сумму для ручного переноса в 1С.

Примеры: зарплата и налоги, амортизация, списание материалов, расчёты для налоговой отчётности.

Расчёт разрешён только после подтверждённого согласованного обновления исходных данных. Повторная отправка того же бизнес-ключа за период архивирует прежний результат и обновляет рабочую строку.

### 2.3. Файлы отчёта

Файл отчёта:

- только читает Access через Power Query;
- не записывает в базу;
- получает факты и готовые результаты расчётов;
- строит печатную или табличную выдачу;
- использует только рабочие таблицы, а не технические архивы;
- разрешает печать и выгрузку только после проверки согласованности среза.

Примеры: расчётные листки, своды по амортизации, регламентированные формы и сверка с 1С.

## 3. База Access

Используется единое логическое хранилище из двух файлов `.accdb` на общем файловом сервере:

- «Учет.accdb» — рабочие факты за все годы, справочники, результаты расчётов, регистры истории действующих значений и служебные таблицы, включая журнал операций;
- «ИсторияИсправлений.accdb» — технические архивы: прежние состояния исправленных или удалённых записей.

Названия обозначают роли файлов; реальные сетевые пути задаются централизованно. Рабочие данные не разделяются по годам в рамках этого решения. Предел 2 ГБ применяется отдельно к каждому файлу. Для работы на компьютере без приложения Access требуется Microsoft Access Database Engine подходящей разрядности. VBA использует DAO с поздним связыванием, Power Query — коннектор Access.

В основном файле находятся таблицы данных, справочники, регистры истории и служебные таблицы. Все таблицы технических архивов находятся в отдельном файле истории исправлений. Экономические формулы и расчёты остаются в Excel. Допускаются специальные формы Access для контролируемого редактирования; прямое редактирование таблиц в Datasheet View не является штатным путём.

Оба файла `.accdb` шифруются паролем базы; общий модуль подключения хранит настройки доступа к каждому файлу. Этот пароль хранится в защищённом проекте VBA каждого штатного Excel-файла и передаётся при подключении через DAO или Power Query. Соединение без правильного пароля запрещено. После открытия соединения файл всё равно обязан пройти отдельную проверку своего постоянного кода и актуальной версии по реестру Access.

Пароль является общим секретом штатных файлов, а не индивидуальной учётной записью пользователя. Он ограничивает случайное прямое открытие базы и обычный доступ без штатных файлов, но не защищает от технически подготовленного пользователя, который извлечёт пароль из VBA. Пользователи, имеющие доступ к рабочим Excel-файлам и сетевой базе, в этой архитектуре считаются доверенными участниками.

### 3.1. Идентификаторы и целостность

- Каждый внутренний первичный ключ — `AutoNumber`.
- Внешний ключ к нему — `Long Integer`.
- Бизнес-идентификаторы хранятся отдельно от внутреннего ID.
- Для каждой таблицы фиксируется бизнес-ключ. Если надёжного естественного ключа нет, это указывается явно и сомнительный уникальный индекс не создаётся.
- Все настоящие внешние ключи между таблицами одного файла используют ссылочную целостность. Межфайловые ссылки технических архивов проверяются общим модулем записи: Access не обеспечивает для них внешние ключи.
- Каскадные изменения и удаления выключены.
- Используемый справочник закрывается через `Активен = Нет`; физически удаляется только ошибочная строка без ссылок.
- Обязательность, допустимые значения и взаимосвязи полей закрепляются типами, `Required`, `Allow Zero Length`, уникальными индексами и `Validation Rule`.

Excel/VBA предварительно проверяет данные ради понятного сообщения, но окончательное решение о допустимости строки принимает Access.

### 3.2. Виды рабочих данных

**Мутируемое состояние** — объект имеет одно текущее состояние, например маршрут рейса или текущее наименование субконто. Рабочая таблица содержит текущую строку, а состояние до исправления помещается в технический архив.

**Накапливаемый факт периода** — строки разных периодов одновременно являются действующими фактами, например зарплата работника за январь и февраль. Рабочая таблица хранит отдельную строку для каждого бизнес-ключа периода. Новая строка следующего периода не архивирует предыдущий период. Архив возникает только при исправлении уже существующего факта того же периода.

### 3.3. Технический архив

Для сущностей, где прошлое значение нужно только для аудита и восстановления, применяется пара таблиц:

- рабочая таблица — одно текущее состояние на бизнес-ключ;
- архивная таблица — снимок строки непосредственно перед `UPDATE` или `DELETE`.

Архив хранит собственный ID, исторический ID рабочей строки, тип операции, дату, автора, ссылку на журнал операций и копию бизнес-полей до изменения. Несколько снимков одного объекта допустимы, поэтому уникального индекса по бизнес-полям архива нет.

Архивные таблицы физически размещаются в «ИсторияИсправлений.accdb». Исторический ID рабочей строки сохраняется как значение, без внешнего ключа к основному файлу; рабочая строка после удаления может отсутствовать. Журнал операций остаётся в «Учет.accdb», поэтому существование указанного ID операции проверяется программно в общем DAO `Workspace`. Снимок и изменение рабочей строки выполняются одной транзакцией, охватывающей оба файла; недоступность архива или ошибка записи запрещает применение всего пакета. Связанные таблицы допустимы для доступа к архиву, но не обеспечивают межфайловую ссылочную целостность.

Технический архив применяется как минимум к рейсам, Регистру бухгалтерии, счетам, субсчетам, субконто и исправляемым результатам расчёта.

### 3.4. Регистр истории

Если разные значения атрибута законны для разных периодов, применяется не технический архив, а регистр истории. Такие регистры остаются в основном файле «Учет.accdb» вместе с рабочими данными за все годы.

Каждая строка регистра содержит объект, значение, дату начала и допускающую `Null` дату окончания. Для одного объекта и вида атрибута периоды не должны пересекаться. Изменение выполняется закрытием текущей строки и добавлением новой в одной транзакции.

Для работников постоянная таблица хранит ID, табельный номер, ФИО, даты приёма и увольнения. Должность, вид деятельности, оклад и другие изменяемые во времени характеристики хранятся в кадровом регистре истории.

### 3.5. Политика новых полей

Перед добавлением каждого поля отдельно документируются:

- экономический смысл;
- дата начала применения;
- смысл `Null`;
- обязательность для новых строк;
- обработка существующих рабочих и архивных данных.

Допустимы подтверждённое ретроактивное заполнение, расчёт из сохранённых фактов, `Null` или достоверное значение по умолчанию. Запрещено подставлять `0`, пустую строку или условный код только ради технической заполненности.

## 4. Основные предметные таблицы

### 4.1. Регистр бухгалтерии

ОСВ по всем счетам и ОСВ по отдельному счёту записываются в одну рабочую таблицу. Файлы ввода остаются разными, но используют общий формат факта.

Единицей отчётного периода и хранения является календарный месяц. Строка содержит остатки на начало и конец месяца и обороты за месяц. Квартальные, годовые и иные составные периоды рассчитываются из месячных фактов и не хранятся как дублирующие строки.

Каждая отправка ОСВ представляет полный набор строк за выбранный период и область отчёта. Частичные или промежуточные ОСВ в Access не загружаются; ответственность за полноту сформированного отчёта несёт пользователь, а формулы Excel подтверждают соответствие нормализованных строк вставленному блоку.

Бизнес-ключ строки состоит из периода, счёта, субсчёта, субконто 1–4, уровня строки, типа данных и других полей, окончательно подтверждающих уникальность выгрузки. Повторная отправка того же ключа означает исправление: прежняя строка архивируется, рабочая обновляется.

Повторная загрузка исправленной ОСВ синхронизирует всю ранее загруженную область отчёта: новые бизнес-ключи добавляются, изменённые строки архивируются и обновляются, неизменные остаются без изменения, а отсутствующие в новом полном наборе прежние строки архивируются и удаляются из рабочей таблицы. Все действия выполняются одной транзакцией.

Отдельная таблица состояний полноты загрузки и признаки «Предварительный» или «Полный» для ОСВ не создаются. Наличие применённой операции означает, что в Access находится последняя полная загруженная версия соответствующей ОСВ. Разрешение изменять данные периода проверяется отдельно по общим правилам раздела 8; повторная загрузка исправленной ОСВ не обходит запрет изменений.

Фактовая строка хранит ссылки на справочники по ID, а не текстовые имена. Суммы и количества хранятся числовыми значениями.

### 4.2. Счета, субсчета и субконто

Справочники разделены на рабочие и архивные таблицы. В рабочих таблицах находятся только актуальные объекты. Для известных однозначных бизнес-ключей используются уникальные индексы:

- счёт — код счёта;
- субсчёт — `ID счёта + код субсчёта`;
- субконто — ключ определяется структурой конкретного справочника и подтверждается при проектировании.

Неизвестные коды и имена выводятся в три дедуплицированных листа разбора. Пустой ID означает создание, заполненный ID — переименование существующего объекта. Каждый лист разбора отправляется отдельно, после чего основной лист ОСВ проверяется и отправляется повторно.

### 4.3. Рейсы

Для рейсов используются две связанные рабочие таблицы: «Рейсы» и «Участки рейса».

Одна строка таблицы «Рейсы» соответствует одному рабочему рейсу — законченной хозяйственной работе, рассчитываемой как единое целое. В ней хранятся `ID` (`AutoNumber`, PK), `Версия`, дата, ссылки на водителя и машину, допускающая `Null` ссылка на прицеп и другие общие свойства рейса. Полный перечень бизнес-полей определяется при проектировании файла ввода.

Одна строка таблицы «Участки рейса» соответствует одному физическому перемещению машины. Минимальные поля: `ID` (`AutoNumber`, PK), `ID рейса` (required, FK), `№ участка` (required), `Откуда` (required, FK), `Куда` (required, FK), тип участка и `Версия`. Для пары `ID рейса + № участка` создаётся уникальный индекс. Например, рабочий рейс `Мастерстрой → ТКЗ` может состоять из участков `База → Мастерстрой`, `Мастерстрой → ТКЗ` и `ТКЗ → База`.

Связь имеет вид «один рейс — много участков» и защищается ссылочной целостностью. Каскадное удаление не применяется. Создание или изменение рейса вместе с его участками считается одной логической отправкой и выполняется одной транзакцией. При контролируемом удалении сначала архивируются и удаляются участки, затем архивируется и удаляется основная запись рейса.

У рейса пока нет надёжного естественного бизнес-ключа. В общем реестре Excel пустой ID означает новую строку, заполненный ID — изменение существующей. VBA загружает также `Версию` строки.

Таблицы «Рейсы архив» и «Участки рейса архив» хранят прежние состояния соответствующих рабочих строк. Изменение выполняется условием `ID + ожидаемая Версия`. Автоматическая эвристика поиска дублей по дате, автомобилю и маршруту сознательно не используется; корректность ID остаётся ответственностью пользователя.

### 4.4. Расстояния между пунктами

Расстояния хранятся не матрицей, а отдельными строками направленных пар: пункт отправления, пункт назначения и расстояние. Предварительный бизнес-ключ — `ID пункта отправления + ID пункта назначения`; направление учитывается, поскольку маршрут `A → B` может отличаться от `B → A`.

Для контролируемого обновления вместе с расстоянием сохраняются дата расчёта и, при наличии, версия или профиль маршрутизации API. Excel может представлять эти же данные пользователю в виде матрицы и рассчитывает их по координатам через API OpenStreetMap.

### 4.5. Результаты расчётов

Рабочая таблица результата хранит отдельную строку на сущность, период и вид расчёта. Отправка нового периода добавляет строку; пересчёт уже существующего периода архивирует прежнее значение и обновляет строку. Конкретные поля проектируются отдельно для каждого расчёта.

## 5. Интеграция с 1С

### 5.1. Основной поток

Пользователь копирует данные из формы 1С, вставляет их в соответствующий файл ввода, проверяет контрольные показатели и отправляет нормализованные строки в Access.

Исходный вставленный блок отдельно не сохраняется ни в Access, ни во внешнем файловом архиве. Нормализованное представление в Access практически соответствует исходной форме 1С; основное структурное изменение состоит в том, что счета и субконто сохраняются как отдельные свойства и ссылки на справочники для удобного обращения к ним. После отправки постоянным источником данных становится нормализованная запись Access.

Точная историческая копия конкретной вставки из 1С восстановлению не подлежит. Это ограничение принято, поскольку отдельное хранение почти дублировало бы те же данные без достаточной практической пользы.

Для ОСВ умная таблица должна приводить суммы и количества к числовому типу. Визуальный столбец проверки сравнивает собранные формулами значения с итогами вставленного блока, но не заменяет общую сверку с 1С.

Контроль перед отправкой выполняется формулами самого Excel-файла. Формулы отдельно получают контрольные показатели исходного блока 1С и рассчитывают соответствующие итоги нормализованной таблицы. Кнопка «Отправить» доступна только при совпадении всех обязательных показателей. Расхождение, пустой контрольный показатель или ошибка формулы запрещают запись всего пакета в Access.

Набор проверяемых показателей определяется формой 1С. Для ОСВ это как минимум начальные остатки, дебетовые и кредитовые обороты и конечные остатки по тем разрезам, которые присутствуют в форме; количества проверяются, если они выгружаются. Сравнение выполняется после приведения значений к точности соответствующего отчёта.

Контрольные итоги и результат такой сверки постоянно в Access не сохраняются. Механизм подтверждает соответствие нормализованных строк вставленному блоку до отправки, но не проверяет последующие прямые изменения базы и не обнаруживает взаимно компенсирующиеся ошибки с одинаковым итогом.

Структура Карточки счёта определяется отдельно для нужных счетов.

### 5.2. Обратный поток

Итоги зарплаты, налогов, амортизации и списания материалов вручную переносятся из файлов расчёта в 1С. После переноса бухгалтер сравнивает общий итог в базе с итогом 1С за тот же период. Отдельный признак переноса по каждой сумме не ведётся.

## 6. Эксплуатация

- Оба файла базы хранятся на общем сетевом ресурсе; пути к ним задаются централизованно.
- Большинство пользователей работают только через Excel.
- Формы Access доступны ответственному пользователю с установленным Access.
- Прямая правка таблиц Access не считается штатной.
- Оба файла `.accdb` открываются только с паролем, передаваемым штатным VBA-кодом.
- Пароль не размещается на листах, в именованных диапазонах, сообщениях об ошибках и журнале операций.
- Сетевая папка доступна только пользователям системы и ответственному администратору; пароль не заменяет права Windows.
- Резервная копия выполняется раз в неделю одним комплектом из обоих файлов при остановленной работе и закрытых соединениях; отсутствие `.laccdb` проверяется у каждого файла. Комплект имеет общую дату и идентификатор. Восстановление выполняется только из одного комплекта.
- Периодическое Compact & Repair необходимо, но регламент пока не определён.
- Следует отдельно контролировать приближение каждого `.accdb` к пределу 2 ГБ. Перенос истории исправлений не увеличивает лимит основного файла и не заменяет контроль роста рабочих фактов.


## 7. Зависимости данных и уведомления об изменениях

Контроль последствий изменения данных является одним из основных требований системы. Для исходных данных, результатов расчётов и отчётов описывается схема зависимостей: какие данные и поля влияют на какие результаты, по каким объектам, организациям и периодам определяется область влияния.

Зависимости задаются явно при проектировании каждого расчёта и отчёта. Экономическая логика описывается пользователем; на её основе создаются реестр зависимостей в Access и правила определения конкретных затронутых объектов в общем VBA-модуле. Автоматическое извлечение зависимостей из формул Excel не является штатным механизмом.

Зависимости относятся к наборам данных, а не только к уже прочитанным строкам. Например, зарплата водителя зависит от всех относящихся к нему рейсов за месяц, включая последующие добавления и удаления. При изменении водителя, организации или даты проверяются старые и новые значения. Для нормативов и регистров истории учитывается период действия, для расчётов за несколько месяцев — все используемые периоды.

При фактическом добавлении, изменении или удалении бизнес-данных система определяет прямые и последующие зависимости и выдаёт уведомление. Оно показывает:

- что изменено и какой операцией;
- какие данные, расчёты и отчёты могут быть затронуты;
- соответствующие объекты, организации и периоды;
- какое действие требуется от пользователя: проверка исходных данных или пересчёт.

Если зависимых результатов не найдено, система явно сообщает об этом. Изменение поля, не участвующего в зависимости, не делает соответствующий расчёт требующим пересчёта. Повторная отправка идентичного набора не создаёт уведомления об изменении бизнес-данных.

Основной режим — уведомление о последствиях, а не автоматический каскадный пересчёт. Пересчёт выполняется пользователем в соответствующем Excel-файле. До него система сообщает о возможном влиянии; точная разница в суммах определяется только после расчёта.

Найденные последствия сохраняются в базе со ссылкой на применённую операцию и остаются видимыми после закрытия Excel. Прочтение уведомления само по себе не подтверждает актуальность зависимого результата. Требование проверки или пересчёта снимается после соответствующего действия и подтверждения актуальности источников. Согласованное обновление Power Query не заменяет такую проверку.

Точный состав служебных таблиц, порядок подтверждения проверки и правила использования результатов, ожидающих пересчёта, проектируются отдельно в соответствии с [03_Открытые_вопросы_и_план.md](../Development/open-questions.md).

## 8. Допустимые периоды изменения данных

Для данных системы должны быть определены периоды, в которых изменение разрешено, и периоды, в которых изменение запрещено. Правила хранятся централизованно в Access и одинаково применяются всеми штатными Excel-файлами и контролируемыми формами Access.

Ограничение распространяется на добавление, исправление, удаление, повторную полную загрузку источника и запись нового результата расчёта. Проверяется экономическая дата или период данных, а не дата нажатия «Отправить». При переносе строки между периодами проверяются оба периода.

До записи система также определяет, затронет ли изменение зависимые данные за период, в котором изменения запрещены. Обычная операция, нарушающая ограничение исходного или зависимого периода, блокируется целиком; сообщение указывает причину и затронутый период. Это относится и к изменениям справочников, расстояний, тарифов и исторических атрибутов, которые способны изменить расчёты прошлых периодов.

Если новое значение должно действовать только в дальнейшем, модель должна сохранять прежнее значение для прошлых расчётов и задавать дату начала нового. Подмена общего текущего значения, меняющая прошлые результаты, не допускается как обход ограничения.

Запрет изменения периода не означает запрет чтения исторических данных. Он также не является признаком полноты или предварительности ОСВ: полнота загрузки и возможность исправления — разные правила.

Конкретные разрешённые интервалы, область их применения (вся база либо организация и контур), ответственный за их установление и процедура исключительного исправления запрещённого периода пока не определены. Они должны быть согласованы до реализации соответствующего контура; произвольные даты или автоматический срок запрета не назначаются.
